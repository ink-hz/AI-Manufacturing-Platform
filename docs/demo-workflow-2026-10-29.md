## 一次性维护工具

文件 `scripts/seed_workflow_demo.py` 与 `scripts/workflow_demo/` 一起部署在维护目录即可。它只依赖标准库和现有生产 `manufacturing_platform.workflow` 包，不依赖 `tests`，不修改服务启动流程，也不需要发布应用包或重启服务。

先由维护负责人确认当前 demo 数据库路径、可信平台目录中的真实负责人UUID，并执行 SQLite 在线备份。工具不会替代目录身份核验或备份。不要从浏览器会话提取身份，不要用真实外部系统凭证。

```bash
PYTHONPATH=/path/to/production/src python /path/to/scripts/seed_workflow_demo.py \
  --workflow-db /absolute/path/workflow.sqlite3 \
  --authority-db /absolute/path/authority.sqlite3 \
  --dataset-id existing-demo-dataset-id \
  --dataset-label '现有模拟环境名称' \
  --owner-id VERIFIED-REAL-USER-UUID \
  --manifest /private/maintenance/realistic-demo-v1.json
```

可重复 `--owner-id` 指定多个经可信目录核验的负责人。参数是维护边界的显式输入，工具不会查找或猜测平台管理员。数据库元数据必须与输入的现有 demo 数据集匹配；生产或其他数据集会拒绝执行。导入前先验证两个存储的元数据，再创建业务对象。

相同参数加 `--verify-only` 用于独立进程读取确认；stdout 是单个 JSON receipt，失败信息在 stderr，退出码非零。完整导入再次执行只验证并返回当前查询结果，不回放任何业务命令，因此用户新增需求、修改承诺和后续推进都不会被覆盖。Receipt 的 `intended_stage` 是原始导入目标；`summary`、`counts` 和 `version` 则来自当前数据。

## 断点和保护范围

- 固定版本 `realistic-manufacturing-demo-v1` 与 dataset ID 决定模拟身份、操作UUID和外部单号命名空间；只授权新创建的模拟项目，不修改平台角色或现有项目成员。
- 每个命令提交前，私有 manifest 先原子保存完整意图，包括实际读取的项目版本。提交后再保存结果。恢复时复用原始意图和版本，允许领域服务返回已提交结果；不把旧命令悄悄改成新版本。
- IO恢复契约：普通命令/授权使用不可变结果版本；`source.pull`和`exchange.dispatch`先提交意图，再提交`exchange.apply`。工具只接受与原意图UUID、项目、执行者、exchange及期望版本唯一绑定的apply审计，并按该次提交确认版本；绝不把实时current版本当作导入器自己的版本。若在IO内部中断、apply缺失/多条或并发版本冲突，停止并要求显式领域对账，不推断成功。
- 权威系统收货/IQC使用稳定外部单号；提交后未写检查点时，通过模拟系统快照识别并校验已存在回执，避免重复入库。随后通过 `source.pull` 进入领域，收货、检验、供应承诺、预留和领用形成真实关联。
- manifest 使用0600文件、原子替换、fsync和排他锁。首次失败永久保留在 `first_failure`；任何失败均停止，已经成功的事务保留。没有整库回滚、删库重建、清空数据或伪造成功状态。
- 原有manifest丢失但命名空间已存在时拒绝继续；dataset、路径或负责人不一致时拒绝继续。导入中若用户并发修改项目，恢复会因版本冲突停止，应人工核对；不要删除manifest或更换版本强行覆盖。
- 完成后的验证核对所有领域操作的意图哈希及模拟源回执，并读取项目、权限和数量。删除或篡改证据会导致验证失败，而不是重造证据。已有合法业务修改不要求保持原始阶段。
- 实际时间按每个来源事件生成并持久化；执行在准备证据与开工之后，测试在执行之后。没有冻结时钟或测试登录。
