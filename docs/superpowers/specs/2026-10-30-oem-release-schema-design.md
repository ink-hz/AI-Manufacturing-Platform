# OEM 发布的数据库兼容回退

用户已授权将已完成的 OEM 功能上线。本补充只修复发布工具在 schema 17→21 后可能错误报告旧版本恢复成功的问题，不修改业务能力、数据集、员工身份或外部集成。

## 裁定与边界

采用前向迁移。相比修改旧版本接纳未来 schema 或回写 schema_version，兼容性探测避免改变数据库语义及新域开工检查。数据库备份用于事故恢复证据，不自动覆盖现有数据库或 WAL。已升级的数据库不以旧代码硬降级。

失败恢复先保留部署锁。确认当前 API 为本次已知旧/新运行态，停止已知目标进程后，以独立 UID10001、network none、只读根、只读制造数据和旧源码挂载的容器执行 stdlib SQLite 只读探测。读取实际旧源码的 SCHEMA_VERSION、唯一版本行与完整数据集身份；不使用 immutable=1，不调用会迁移的 WorkflowStore。只有版本与旧源码完全相同、身份匹配且探测成功，才允许旧 Compose 重建。没有配置 workflow 的历史发布保留原流程。

不兼容或未知时不执行旧 Compose，不更新数据库元信息；恢复本流程停止的同一目标容器，保留发布锁及拒绝记录，标明 forward_repair_required。停止、探测、重启和收据失败均不能变成恢复成功。成功恢复旧运行态必须额外执行旧代码自身 READINESS_CODE，再写 restored:true，之后才释放锁。

维护记录明确前向迁移后的旧源码回退限制。完整现有运行态、48 项有序配置输入、15 挂载、其他容器、源与静态文件及 Nginx 均受原发布校验保护。本次平台源码固定为实际线上 b4c258b4fd386f0decafeb1555e93eae6bcc323e，不携带其他平台主线修改。

## 验证

用真实 SQLite 和独立 Python 子进程验证版本17允许、版本21拒绝且不写库、数据集错误/未知版本/错误路径拒绝，以及 WAL 可见性。故障注入验证 stop→probe→old-compose→readiness→receipt 的顺序、不兼容时只恢复同一目标并保留锁、收据与探测失败关闭回退。保留现有部署回归。候选 Linux 继续执行完整36场景；生产不灌入合成身份或业务记录。

候选随后在独立子目录直接调用已有纯Python的OEM socket验收函数，复用其真实断言和已提交样例依赖，并指向实际挂载的业务源码。该结果与原36场景分别记录；不引入pytest安装或生产业务数据。

## Linux只读WAL探测修订

实际固定镜像SQLite3.40.1下，1843200字节的WAL模式schema17库没有WAL/SHM侧文件；对只读绑定目录直接mode=ro打开得到SQLITE_CANTOPEN。相同文件复制到私有tmpfs后可读出17，且线上源文件的身份、时间戳和SHA256均未改变。这是探测方式与SQLite元数据机制的边界问题，不放开生产数据挂载写权限。

权威回退探测在原有停止目标/排除其他写入者之后，固定采用私有副本这一条路径。生产数据和旧源码仍只读；辅助容器新增32MiB临时tmpfs，主库与WAL合计上限16MiB（当前库约1.76MiB），超限拒绝回退。复制前后验证打开文件和路径身份、大小、mtime/ctime、侧文件存在性及SHA256；不复制SHM，发现rollback journal即拒绝。只复制当前主库及匹配WAL，SQLite仅在临时副本目录重建共享内存；对副本mode=ro/query_only读取，结果关联回原始库身份。任何源变化、未知状态或错误都保留原有拒绝/锁策略；不尝试直接打开失败后的自动替代路径、不使用immutable=1、不修改原库。

关键回归是主库仍17、已提交21仅在WAL时必须观察到21并拒绝旧代码；同时验证无侧文件的17允许、SHM不复制、源字节不变、变动/超限/journal拒绝，并再次通过实际Linux只读挂载探测后才可发布。
