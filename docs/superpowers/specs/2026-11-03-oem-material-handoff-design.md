# OEM 物料交接与线边可见性设计

日期：2026-11-03

业务依据：OEM 痛点 P14（手工交接，无法确认是否领走）和 P15（手工交接，物料位置不易定位）。用户已同意优先实现该方向，并要求完成后从繁琐流程中反思核心需求、简化产品。

## 1. 核心结果与本期边界

回答四个问题：本笔物料交给谁、实际收到多少、收到哪里、差异由谁处理。

交接记录是人工确认的实物交接凭据。它关联已有 OEM 项目、物料批次和可选工单，明确交接双方、数量、位置和时间。它不自动改变物料所有权、库存、预留、IQC 合格量、耗料或 SAP 过账；真实 WMS／MES 对接后另按权威契约确认。

同一批次可分成多笔交接，界面逐笔显示数量和位置，不能以最后一笔位置冒充整批物料的唯一位置。待接收记录只表明交出方已登记，目的位置仍待接收确认。

新交接写入仅用于 `mode=oem` 的项目。历史自有产品项目、既有业务和数据保持可读取，不为范围变化删除或改写原数据。

## 2. 简化后的产品流程

1. 在“计划与物料”的“物料交接”入口发起交接，选择现有批次、接收人，填写交接数量、起点和目的位置。单位来自批次；工单和发生时间为可选补充。
2. 指定接收人打开待办，默认带出数量和目的位置，核实后确认。实际数量或位置不一致时必须填写差异说明。
3. 有差异的记录保持“待处理差异”；交出人或项目负责人／平台管理员记录处理说明，原交出、实收数量和位置均保留。
4. 未接收的错录交接可由交出人或项目负责人／管理员填写原因取消；已接收记录不能以取消抹去实物记录。

核心表单不要求用户输入后端 UUID、来源系统、来源版本、JSON、数据库路径或操作幂等编号。调用身份和记录编号由系统产生；人工来源持续显示，技术凭据及完整历史按需展开。

默认台账围绕“待接收、待处理差异、全部记录”。旧供应、到货、预留等能力继续可访问。新功能不增加独立顶级导航。

## 3. 对象及命令契约

对象类型：`material_handoff`。

共用现有命令的 `operation_id`、`expected_version`、可信 Actor、项目授权、CSRF、CAS、幂等及审计。

### material_handoff.record

字段：`material_lot_id: UUID`、`work_order_id: UUID|null = null`、`quantity: Quantity`、`unit: Name`、`from_location: Name`、`to_location: Name`、`receiver_id: UUID`、`occurred_at: AwareDatetime|null = null`、`note: Text|null = null`。

约束：批次和可选工单归属同项目；单位、精度按批次；数量为规范十进制正数并检查存储范围。起点与终点为非空且不同的实际位置文本；接收人是同项目当前有效成员且具有仓储／生产／供应／项目负责人角色，交出人和接收人不同。管理员自身成员身份可复用现有规则，但不能伪造另一个人的接收签名。发生时间默认业务时钟，显式时间必须带时区且不在未来。保存交出人和接收人身份及可信姓名快照，姓名通过现有受控成员查询解析；没有名称时保留真实身份，不接受客户端伪造名称。

交接编号由服务端生成，使用真实身份及人工来源标识。登记不声称已收到，也不据交接数量校验或推算权威库存余额。

### material_handoff.receive

字段：`handoff_id: UUID`、`received_quantity: NonnegativeQuantity`、`received_location: Name`、`occurred_at: AwareDatetime|null = null`、`note: Text|null = null`。

仅指定接收人且当前仍具备适用角色可确认，管理员不能代签另一接收人。只接受 pending 状态。实际数量允许为零或高于交出数量，以如实登记差异，仍遵守批次单位精度和数值范围。实收数量或位置任一不一致时 note 必填，状态 disputed；一致则 received。接收时间不得早于交接发生时间或晚于当前业务时钟。接收记录一经写入不能覆盖。

### material_handoff.resolve

字段：`handoff_id: UUID`、`resolution: Text`。仅 disputed 状态，交出人或项目负责人／管理员可办理，继续核验当前项目角色及只读状态。追加处理人、处理说明和时间，状态 resolved；不覆盖原交接和实收事实，不把差异数量改成相符。

### material_handoff.cancel

字段：`handoff_id: UUID`、`reason: Text`。仅 pending 状态，由交出人或项目负责人／管理员办理，追加取消事实，状态 cancelled。

### 状态与读接口

状态为 `pending | received | disputed | resolved | cancelled`。使用现有项目对象列表、对象详情、全局台账、任务和仪表盘协议，分页排序在 SQL 中完成。

详情保留批次和工单关系、数量单位、位置、双方身份、人工来源、交接／接收／处理／取消事实及审计。服务端 next_actions 必须同时匹配角色、当前状态和指定责任人。接收待办归接收人，差异待办归交出人；撤权或只读后不能暴露可写动作。

## 4. 实现组织

后端增加独立模型、schema、业务与查询模块；注册到现有 command/object registry。schema21 以新增表及索引前向迁移到22，保留现有业务行及 authority 数据库。新建库也包含同样表。禁止把旧工程资料 `handoffs` 表当作物料交接复用。

前端增加独立交接类型、表单、台账和详情组件，复用现有 API、草稿保护、冲突保留、成员列表、项目过滤及权限处理。放入现有“计划与物料”导航，可从全局台账、项目和待办打开同一记录并保持返回上下文。

首期不添加多级审批、工作流配置器、独立库位主数据、扫码设备驱动或通用规则引擎。扫描枪可按普通输入方式查找记录；不得声称已连接 WMS/PDA。

## 5. 需要验证的行为

- 发起、准确接收、数量短收／多收／零接收、位置偏差、差异处理、未接收取消和非法状态迁移。
- 批次／工单跨项目、错误单位或精度、空位置、同位置、无效接收人、代签、角色撤销、只读、CSRF、CAS、幂等及并发接收。
- 同操作同内容重放返回原回执；同操作不同内容拒绝；状态推进不能破坏合法重放，同时保留实时授权核验。
- 每一步均不改变库存、IQC、预留、耗料、所有权和 authority 记录。
- schema21 升级后原数据保留；重启后事实与待办可读；分页不扫描无关项目，待办不越权。
- 前端可通过业务字段完成完整流程；默认数量和位置可核对；错误保留输入；切换项目或撤权不会出现旧数据。
- 产品复盘检查默认必填项、重复输入、技术字段、主操作和低频操作；保留必要事实与异常，而非删掉业务约束。

## 6. 交付与实际接入

本期交付可测试的软件流程、需求与产品取舍记录、迁移说明和回归证据。生产部署及真实 ERP／MES／WMS、扫码设备与现场验收另按实际条件安排，不以模拟或人工记录替代已接入声明。
