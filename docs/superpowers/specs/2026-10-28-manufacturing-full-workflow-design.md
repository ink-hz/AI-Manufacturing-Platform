# 制造全流程产品补充设计与 mock 验收范围

日期：2026-10-28。状态：**待用户审阅的产品范围草案，尚未进入本轮实现或验收**。

依据：[制造系统手册](../../manufacturing-system-handbook.md)第 4 章三条数据流、S1—S9、第 14—16 章；[当前 v0.5 产品设计](../../manufacturing-workbench-product-design.md)。本文件扩展后续产品范围，不将规划能力描述为现有线上能力，不改动手册原文。

## 1. 本轮目标与方案选择

交付能够实际操作、持久化、回看证据的制造管理流程，并使用相机、数采相机、3D 打印机、OEM 机器人四组模拟业务验证正常路径及异常回流。全流程验收指需求受理至交付、结案和质量反馈，覆盖业务状态、数量、版本、权限、来源与审计。

| 方案 | 能验证什么 | 取舍 |
| --- | --- | --- |
| 真实业务模型与服务，外部系统适配器 mock（推荐） | 平台内部完整规则、对象关联、跨系统状态及异常恢复 | 先设计数据契约；外部正式连接另行验收 |
| 页面使用固定 JSON 和预设成功动作 | 布局、展示和部分交互 | 无法证明持久化、权限、数量约束、异常闭环与真实接入能力 |
| 同时自建完整 ERP/MRP/MES/PLM | 自有业务系统的全部内部运算和执行 | 与已有采购系统职责重叠，范围与成本远大于本轮 |

推荐第一种。mock 位于明确的外部边界，平台的状态机、权限、版本校验、数量核对、持久化及审计真实执行。MRP/排程/财务结果由模拟权威系统按固定输入版本提供，不把平台扩展为另一套 MRP/成本引擎。

## 2. 产品定位和系统分工

平台提供制造协同、业务状态汇总、异常处理和追溯入口。正式数据归属延续现有系统协同配置：

| 责任 | 正式权威或执行方 | 平台负责 |
| --- | --- | --- |
| 订单、工单创建、库存账、财务成本 | ERP | 关联正式编号、保留承诺版本、展示来源回执与差异 |
| 计划、需求展开、排程 | ERP-MRP / APS | 提交受控协同申请、接收有版本的结果、处理缺料和例外 |
| BOM、工程版本、生效规则 | PLM/PDM 或已裁定的来源 | 关联资料包、影响对象、交接与切换完成证据 |
| 过站、用料、报工、SN 履历 | MES 或经核实的人工载体 | 接收执行事实、关联任务和异常、查询正反向履历 |
| 收货、库位、备料、发料 | WMS/ERP | 汇总数量和状态、跟踪差异、展示对方处理结果 |
| 检验、处置、正式放行 | QMS/经授权质量主体 | 分离原始结果、处置与放行，维护约定前置条件 |
| 供应商交期、客户批准和验收 | 对应外部主体 | 保存承诺、版本、责任、凭据及接收时间 |

真实接口未接入时，用户录入的是人工登记事实；模拟接口返回的是演示环境模拟事实。收到、校验通过、业务批准、执行系统接受、正式过账分别展示。平台准备通过只表示协同条件满足；正式开工/冻结/发运是否已执行必须等待权威系统回执。

库存预留由权威系统原子接受。平台的计划分配或已提交请求不视为实际预留；确认数量、余额和源版本以权威回执为准。mock 权威端必须维护可变余额并执行同样的原子约束，以便模拟并发冲突与部分接受，而不是用平台本地数字冒充库存过账。

## 3. 产品中的核心对象

项目是协作范围；订单行代表交付义务；工单代表生产执行范围；批次/SN 标识实物。对象之间通过有数量、版本和来源的关联记录连接，不通过备注推断，也不默认一项目一工单。

| 对象 | 必须表达的内容 |
| --- | --- |
| 制造项目 | 内部/外部、业务线、协作成员、产品、责任范围；保留当前项目/阶段/事项 |
| 需求与订单行 | 询价/预测/正式需求、产品配置、数量单位、原始承诺、当前承诺、变更理由和评审依据；正式单据来源 |
| 履约分配 | 订单行与工单/合格产出/发运的关联及分配数量；允许受控拆单，防止重复分配和超交 |
| 物料与工程引用 | 权威料号、客户料号映射、单位、受控 BOM/路线/固件/测试版本；本平台只维护其关联及快照 |
| 工程变更 | 旧版/新版、生效工单或批次/SN 边界、客户批准、受影响采购/库存/在制、处置与切换证据 |
| 计划与供应事实 | 来源计划版本、需求行、采购/客供、承诺交期、在途、实收、合格、冻结、预留数量及数据截点 |
| 生产工单 | 正式来源、数量单位、执行版本快照、计划日期、分配/拆分关系、准备结论、执行方回执 |
| 实物与执行记录 | 工单、批次/SN、工序、设备/人员引用、物料批次、版本、数量、发生与登记时间；原始事件保留 |
| 检验与不合格 | 对象、实测值/单位/限值/程序版本、首测与复测、缺陷、处置、返工、证据和批准主体 |
| 放行与交付 | 制造/质量/客户放行各自独立；箱/SN、分批发运、签收、验收、遗留项与数量分别记录 |
| 结案与反馈 | 履约关闭、质量关闭、成本结案分别有来源；RMA、CAPA 效果验证及回流 ECO/供应/工艺的关联 |
| 交换记录 | 来源系统、源对象与版本、业务幂等标识、方向、各阶段回执、错误、人工处理和对账差异 |

统一规则：对象使用稳定标识；关联保存业务范围与数量；不可变版本/事实追加，纠正通过新事件表达。可变记录沿用 CAS 与操作 UUID。外部编号唯一性按来源系统、对象类型和业务编号定义，不能用显示名称去重。

## 4. S1—S9 的实际业务动作

| 阶段 | 操作与输出 | 关键限制与异常回流 |
| --- | --- | --- |
| S1 需求与评审 | 登记来源，区分预测/正式需求；分别记录技术、物料、产能、交付条件；关联正式订单 | 受理不自动批准采购/投产；改期保留原承诺；数量/取消变更需评估已分配和已执行范围 |
| S2 工程与工艺 | 复用资料包、独立回执和固定修订；补充变更影响和生效边界 | 新版本不改旧工单快照；客户批准未知不满足相应条件；旧料/在制处置未完成则变更保持未关闭 |
| S3 计划与供应 | 导入/模拟接收计划版本，查看工单、需求与供应关联，分派缺料和延期例外 | 原始承诺保留；计划结果带输入版本与截点；缺失、过期或未核实依据不能显示计划已确认 |
| S4 物料与资源 | 区分自购/客供，跟踪承诺、到货、IQC、合格和预留；关联设备、人员准备 | 在途、实收不等于合格可用；所有权、状态、单位和分配范围必须匹配；差异回采购/供应主体 |
| S5 工单与开工 | 关联正式工单与版本；复用准备核对，区分首件计划/结果；提交开工请求并等回执 | 缺料、版本不一致、校准过期、首件未通过、必需客户确认缺失均保持未就绪；不把请求提交当开工成功 |
| S6 执行与异常 | 导入/模拟过站、用料、报工和停工事实；关联批次/SN、工艺与测试版本 | 缺料回 S3/S4；返工走独立路线并复测；防止重复事件、负数量和超范围回报；保留失败和纠正记录 |
| S7 测试与放行 | 原始测试、复测、不合格处置；制造、质量、客户三个独立放行结果 | 限值与程序版本匹配；受控角色批准；失败不被复测覆盖；有条件放行必须限定对象与数量 |
| S8 分批交付 | 关联箱/SN、来源出库/发运；记录签收、约定验收和差异 | 未满足必需放行不得提交发运；只发一部分不能关闭整行；签收不自动表示验收完成 |
| S9 结案与反馈 | 展示 ERP 成本结案；独立关闭履约与质量问题；退货分析、CAPA 验证并回流 | 成本结案不自动关闭客诉；RMA 与原批次/SN/发运关联；CAPA 有效果验证，ECO 有执行结果 |

项目 S1—S9 状态作为协作进度保留；涉及工单、放行、交付数量的结论由对应业务对象聚合。手工完成阶段不得覆盖正式单据、未完成交接、未满足准备项或未关闭的必需业务条件。

开工分为首件试做与批量执行：版本、人员、设备及首件所需物料就绪后，按授权允许首件试做；首件结果满足要求后才允许相应批量范围执行，避免把首件通过设置为首件试做本身的前置条件。新建全流程项目明确启用必需业务对象和检查范围；历史项目保持原范围，不因缺少新对象被自动改判。

## 5. 内部与 OEM 差异贯穿流程

内部相机、数采相机与 3D 打印机采用共同对象模型，按产品配置资料/工艺/测试与追溯要求。数采相机是否为独立业务线保持可调整，不硬编码成组织层级。

OEM 项目另有明确字段及规则：设计与关键变更批准主体、客户/厂内版本映射、逐项供料责任、客供料所有权、消耗/损耗和余料对账、客户测试和标签规范、客户放行是否必需及其验收位置。代工代料允许自购、客供或混合；未确认的合同条件保持未知，阻塞其对应动作。

## 6. 用户、责任与权限

以下为本轮建议分工，不宣称已经是公司正式制度。具体人员从可信身份与业务授权配置关联，责任人的文本姓名不产生权限。

| 业务角色 | 操作范围 |
| --- | --- |
| 项目/业务负责人 | 需求受理、评审协同、承诺变更申请、履约跟踪 |
| 工程 | 资料核对、工程变更、版本与切换证据 |
| 计划 | 计划版本、工单分配、例外处理和准备协调 |
| 采购/供应协同 | 供应承诺、催交、到货与差异跟踪 |
| 生产 | 授权工单的执行/异常登记，查看有效作业依据 |
| 质量 | 授权范围的检验判定、不合格处置和质量放行 |
| 仓储/交付 | 收发料回执、箱/SN、发运及签收验收跟踪 |
| IT/配置管理 | 系统、接口和权限配置；配置权限不自动等于业务签批资格 |
| 外部主体 | 后续真实客户/供应商门户只允许查看自身授权对象，本轮通过隔离 mock 模拟其输入 |

权限按对象、项目范围、业务动作和数据源在服务端校验。质量签批、客户确认等动作必须具有对应业务资格；平台管理员身份本身不伪造这类批准。测试角色由独立测试身份与授权夹具提供，不能通过前端角色选择绕过服务端授权；生产身份、CSRF、只读和审计边界保持。

## 7. 页面与日常使用

保留独立管理平台外壳、用户菜单、草稿保护、事项中心和整篇手册。产品以待处理业务和具体单据组织，导航只在实际功能交付后开放。

| 工作区 | 用户直接处理的内容 |
| --- | --- |
| 工作台 | 我的待办、缺料/延期、版本待接收、开工缺项、待放行/验收；可定位对象 |
| 制造项目 | 项目概览与阶段、工程资料、关联订单/工单、异常、交接及完整履历 |
| 订单与交付 | 需求评审、订单行、原始/当前承诺、分批履约和验收 |
| 计划与物料 | 计划版本、需求/供应明细、缺料、客供和合格可用依据 |
| 工单与执行 | 固定版本、准备、首件、执行回执、返工与在制异常 |
| 质量与追溯 | 测试/不合格/放行，按 SN/批次正反向查询，RMA/CAPA |
| 事项、系统协同、制造手册 | 延续现有能力；系统协同增加交换记录和对账差异 |

单据详情统一给出当前状态、数量、版本、来源与截点、待办/下一动作、相关对象、证据与历史。项目不复制整个业务台账；从项目和事项进入同一正式对象。统计点击可下钻到明细，不显示无依据的 OEE/良率/交付率。

## 8. mock 的边界与数据设计

测试与演示使用独立数据库/数据目录、独立身份夹具和明确的 mock 连接配置；既有线上真实和演示记录保留，不为本轮全流程测试清库或覆盖。

mock 适配器实现 ERP、MRP/APS、PLM、MES、WMS/QMS、供应商、客户所需的最小读写契约。采用可复位的模拟外部状态，不一律返回成功：提交后生成可查询回执，并能配置超时、重复、乱序、拒绝、部分数量、过期版本和数据错误。文件导入路径使用相同的校验与持久化服务，解析失败不写业务成功状态。

每笔交换保存：来源/模式、源对象与版本、业务标识、事件/采集/接收/处理时间、单位及精度、回执阶段和错误。超时先查询处理结果；重复相同业务只产生一次结果，同标识不同内容明确冲突；乱序旧版本拒绝；对账同时比较明细与合计。

演示界面持续标明“模拟数据/模拟回执”；所有汇总沿同一数据环境计算。复位只清理本次测试拥有的隔离数据。真实对接验收另外检查接口资料、实际权限、真实样例与对账结果，mock 通过不显示“生产已连接”。

## 9. 开发拆分与统一验收

这是跨多个子系统的产品范围，分四个可独立评审的子项目实施；每个子项目先完成详细模型/接口/交互设计与实现计划，再写代码。

| 子项目 | 交付范围 | 结束条件 |
| --- | --- | --- |
| A 业务主线与权限 | 需求/订单行、关联数量、正式工单引用、受控业务角色、mock 契约骨架；复用现有工程准备 | 需求→正式订单→工单→现有开工准备可操作，权限与原承诺保护通过 |
| B 供应与执行 | 计划/供应事实、合格可用与占用依据、客供、执行事实、版本切换和异常回流 | 缺料→到货→检验→准备→开工/执行回执闭环通过 |
| C 质量、交付与反馈 | 测试/返工/放行、批次/SN、分批交付/验收、独立结案、RMA/CAPA/ECO | 正反追溯、失败与复测、分批交付及质量反馈闭环通过 |
| D 全流程联测与交付 | 四组主剧本、跨模块异常、多角色越权、接口故障、重启和全量汇总核对 | 所有约定场景通过或明确记录阻塞；可供用户实际操作验收 |

前三个子项目的局部通过不宣称整套工作流完成。最终执行[验收矩阵](../../testing/manufacturing-full-workflow-acceptance.md)，报告通过、失败、阻塞和未执行，逐项提供源提交、业务标识、期望/实际状态、持久化/审计证据及耗时。

依既有约定，开发侧负责接口、业务数据、持久化、进程恢复和前端组件测试；桌面/手机视觉、真实角色实操由用户验收。mock 联测、真实系统集成、生产验收和业务改善四种结论分别记录。

## 10. 本轮范围边界与自检

本轮目标为可操作的全流程协同与模拟联测。真实 MRP/APS 运算、财务成本计算、工业设备控制和真实客户/供应商消息发送由各自权威系统及另行接入承担。制造域 AI 以已核实数据和权限为依赖，后续单独设计；本轮不以规则模板或假 AI 分析代替业务能力。

保留现有库、旧项目、资料包/固定修订、独立交接与准备记录、审计及手册。历史项目缺少新对象时不自动补造订单和工单。后续迁移需增量且可回退；具体 API/表结构/权限映射在各子项目详细设计中确定，不声称本总体范围已经能直接替代实现计划。

自检：覆盖 S1—S9 和四种业务剧本；将模拟外部结果与内部真实规则分开；明确对象、数量、版本、权限及异常恢复；建设与验收分层；无未来能力上线声明。待用户审阅本范围后，先进入子项目 A 详细设计与实施计划。
