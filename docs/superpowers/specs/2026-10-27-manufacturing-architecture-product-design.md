# 制造手册架构的产品化迭代

状态：用户已于 2026-10-27 以“开始吧”批准本轮设计，进入开发；实际发布以发布记录为准。

日期：2026-10-27。当前产品基线为制造源码 `161292be7c01038cc7c25b5f36aea04577c19823`，此前的连续阅读修正保持。本草案通过后作为 v0.4 的实现依据；现行 v0.3 在此之前继续有效。

## 1. 要解决的问题

当前工作台可以维护项目、阶段、事项和操作动态，但 `Handoff` 只有名称、交接双方、版本说明和备注；`SystemRelationship` 只有系统名称、对象描述、维护人、方式和备注。它们无法回答：这批生产依据哪组版本、资料实际交给谁、下游接收的是不是同一版、开工缺项是否关闭、哪个系统的记录是正式来源。

本次把手册的对象、责任和交接规则变成可操作的业务能力。手册继续是一份完整文档，不作为产品导航树，不再拆分章节。

设计依据：[系统手册](../../manufacturing-system-handbook.md)第 2 章分层、第 4 章三条数据流、S2 工程准备、S4 物料与产能、S5 开工检查、第 14 章数据权威与接口契约、第 15 章平台与 AI、第 16 章建设次序。

## 2. 路径选择

| 路径 | 能交付什么 | 代价与适用范围 |
| --- | --- | --- |
| 业务对象与交接驱动（推荐） | 在项目中实际维护资料包、版本、回执、核对条件和问题；系统架构约束来源与数据归属 | 需要持久化对象与状态规则，能逐条业务闭环扩展 |
| 先做架构总览与系统盘点 | 直观看到系统、负责人和现状 | 主要用于盘点，项目交接和执行仍依赖文字 |
| 自建完整 ERP/MES/PLM | 深入订单、库存、工单、工程与车间执行 | 与现有采购系统边界不清，需真实主数据、制度及接口资料，超出本轮范围 |

采用第一条路径，系统盘点作为配置能力随业务闭环一起落地。

## 3. 架构如何进入产品

### 3.1 三条数据流成为业务组织方式

| 手册主线 | 产品中的业务对象 | 当前迭代与后续衔接 |
| --- | --- | --- |
| 产品定义流 | 产品与料号引用、EBOM/MBOM/图纸/SOP/固件/测试规范版本、工程资料包、交接回执 | 本轮建立版本包、来源与交接；后续扩展 ECO 生效和旧料/在制处置 |
| 订单—计划—执行流 | 需求/订单依据、计划与工单引用、供应承诺、备料与资源核对、执行回执 | 本轮关联项目需求、外部工单依据、备料和资源核对；后续扩展供应明细与真实计划/执行接口 |
| 质量—追溯流 | IQC/首件/测试/OQC 证据、制造方/质量/客户放行、批次/SN、交付验收 | 本轮接纳开工所需质量与校准证据；后续单独建立检验、放行、追溯与交付对象 |

相机、数采相机、3D 打印机和 OEM 共用对象框架，资料适用项、客户批准责任、供料所有权与验收要求分别配置。内部/外部仍是业务分类，具体产品业务线可以继续调整。

### 3.2 分层体现为产品职责

| 手册架构 | 产品能力与页面 | 数据含义 |
| --- | --- | --- |
| 经营与计划层 | 项目交付目标、需求依据、外部订单/计划/工单引用 | 保留承诺依据；平台上的目标日期不自动修改 ERP 客户承诺 |
| 制造运营层 | 阶段工作区中的资料交接、准备核对、问题处理，后续扩展执行与放行 | 围绕实际项目和业务对象协同 |
| 系统与集成 | 系统登记、数据归属、交接记录与待处理项 | 明确对象来源、业务编号、版本、责任、接收状态和处理证据 |
| 数据底座 | 对象标识、来源、版本快照、事件时间、审计与指标口径 | 记录可核对、可追溯，保留历史 |
| BI 与 AI | 首先显示真实未交接、缺项与逾期待办；具备数据后扩展分析和受控动作 | 不填充模拟产量、良率、OEE 或虚构 AI 结论 |

ERP/PLM/MES/WMS/QMS/EAM 等名称是职责类别。实际系统产品、安装现状和接口能力由用户登记与核实，不根据手册预填为公司已部署事实。MRP 可以是 ERP 的模块，不强制登记成另一套独立系统。

## 4. 本轮完整交付范围

本轮限定为一个子项目：**工程资料到开工准备的协同闭环**。它同时建立后续三条主线共用的系统、来源、版本、交接和证据能力。

### 4.1 页面结构

保留“工作台、制造项目、事项、制造手册”，新增“系统协同”。首页继续围绕实际项目与待处理工作，不以系统分类、架构图或知识章节铺满屏幕。

- 工作台：把“待补工程资料、待接收回执、准备缺项、逾期交接”加入真实待办；点击直接进入所属项目与对象。没有记录时给创建入口，不显示演示数据。
- 项目详情：保留 S1—S9 和阶段操作，在 S2 提供“工程资料包”，S4/S5 提供“生产准备”。项目内可查看全部已建资料包和核对记录，实际记录不因阶段切换消失。
- 事项：继续聚合任务、问题和确认事项，新增来源对象链接；从缺项创建的问题能返回原资料包或核对项。
- 系统协同：有实际记录的系统列表与详情，提供数据归属配置和跨项目交接队列。系统详情可查看职责、责任人、相关对象和未完成交接；有新增、编辑、停用等真实操作。
- 制造手册：保持全文连续阅读，支持从业务上下文定位后返回。

系统配置使用紧凑列表/详情，业务主界面使用项目工作区和待处理项。所有按钮对应已实现的读取或写入行为，后续规划不以空模块或失效按钮提前出现。

### 4.2 系统登记与数据归属

系统登记字段：实际名称、职责类别、适用业务线、业务责任人、IT 维护人、使用现状、交换方式、说明。使用现状采用手册的四态：已购未用、已用但绕行、无系统但有效、确实缺失；未核实记录独立标注。Excel、纸质台账、客户资料平台也可以作为实际记录载体。

交换方式为未知、人工、文件、API。填选 API 只表示计划或现状描述，本轮没有网络连通验证和凭证配置，不出现“已连接”“同步成功”的绿灯。

数据归属按“业务线 + 对象类型”明确正式来源与修改/过账入口，例如工程 BOM 归 PLM、物料主数据归 ERP。手册中的建议作为帮助文字；用户确认后才成为该业务线的配置。同一范围同一对象不允许同时存在两个有效正式来源，历史约定保留。MBOM 归 ERP 还是 PLM 由实际业务配置。系统停用不删除已有引用和历史证据。

### 4.3 工程资料包

资料包对应一个制造项目的一组执行依据，记录产品/料号引用、适用工单/批次/日期范围、资料提供方、核对负责人及资料明细。资料明细包含资料类型、名称、源编号、源版本、来源系统或载体、来源责任人、凭据引用、适用性及核对状态。

支持的资料类型：设计 BOM、制造 BOM、图纸、工艺路线、SOP、固件、测试程序、测试规范/限值、其他受控资料。不同产品按实际勾选适用项；“不适用”必须有原因和操作者，不默认给全部业务线强加同一套文件要求。

资料包流转：草稿 → 待核对 → 核对完成；发现问题可退回并说明原因。“核对完成”表示平台内人工核对，不代替 PLM 发布或客户工程批准。正式发布/批准状态作为独立外部依据记录，保留原编号、版本与凭据；未知则显示未知。

核对完成后冻结该次资料快照。后续更改生成新修订，保留旧版及前后关系；不能把历史工单引用悄悄换成最新版。OEM 分别记录客户版本、厂内版本、批准责任方和客户批准依据；客户批准未知不能显示客户已批准。

### 4.4 交接与接收回执

交接记录绑定资料包的固定修订，并记录业务唯一编号、发送方、接收方/目标系统、负责人、目标日期、交接方式、交接凭据和事件时间。

状态：草稿、已登记交出、已登记接收、退回、撤销。这里的动作是平台内登记：不会自行向供应商、客户或其他系统发消息。外部交接、接收时间来自凭据；平台登记时间和登记人另行记录。登记接收必须说明接收对象、收到的修订和回执依据；版本不一致或缺少依据时不能登记为已接收，应退回或保持待处理。

一次下发可以有多个接收方，每个接收方保留独立回执。不能由“已登记交出”推断“已接收”，不能由登记接收推断对方系统已过账。

### 4.5 生产准备核对

由项目成员显式建立一份核对记录，绑定项目、外部工单/批次依据、数量引用和具体资料包修订。选择本次适用的必需检查项后保存为范围快照；以后模板变化不影响已建记录。

首批检查范围：工程资料与适用版本、物料齐套依据、设备/治具就绪及校准有效期、人员准备、首件安排/结果，以及 OEM 约定的客户确认和客供料条件。首件计划与首件检验通过分开记录；“已安排首件”不能满足需要首件通过的批量开工条件。

每项保存责任人、预计完成日、核对状态、来源与凭据、核对时间、核对人、阻塞原因。状态为待核对、已核对、有缺项、不适用；不适用须说明理由。物料项分别记录自购/客供/混合责任及相应凭据，客供料仍参与齐套核对；本轮不根据手填数量自动计算库存可用量或 MRP，也不把供应商承诺到货当作合格库存。

涉及校准/效期的必需项额外保存有效截止日；核对记录保存计划使用日期。日期缺失或有效期不覆盖使用日期时，服务端拒绝将该项保存为已核对。测试程序与限值等版本项必须引用资料包内对应修订，不能只填写“已确认”备注。来源批准明确撤回或凭据失效时，原结论作为历史保留，当前受影响项回到待核对并显示重新核对原因；人工登记者与依据可追查。

总体结论由服务端根据这份记录的必需项计算：待核对、有缺项、核对完成。不允许靠总状态下拉框绕过缺项。材料版本、适用范围或关键依据改变后，旧核对结论保留为历史，新版本重新核对。核对完成不等于 ERP 工单已下达、MES 已允许开工或 QMS 已批准放行。

从缺项可创建关联问题并指定负责人；问题完成和核对通过是独立动作，完成任务不会自动伪造条件满足。阶段“完成”也不覆盖这份核对结论。

显式启用后的必需核对记录纳入项目完成条件：所有阶段、事项和已启用的必需核对均完成，项目才能汇总为已完成。有缺项进入受阻提示；待核对进入未完成待办。旧项目不会被自动补建核对要求，也不因缺少新对象失去可读性。

## 5. 跨业务差异与示例验收

以下均为一次性验收场景，不写入生产作为真实记录。

1. 相机试产：建立工程资料包，关联 BOM、固件、测试程序与限值版本；给制造与测试分别登记交接。一个接收方退回错误版本，工作台能定位问题；更正时保留旧版和退回依据。
2. OEM 机器人：分别记录客户设计版本、厂内 MBOM 和客户批准依据；选择自购与客供责任。客户确认缺失时，对应准备项保持待核对；其他资料齐全不代表客户批准完成。
3. 准备核对：齐套凭据已记录，但治具校准过期或首件只有计划时，对应必需项不能满足。修正依据后重新核对，保留原先的缺项记录、核对人与时间。
4. 变更：已完成核对的资料包产生新修订，原工单引用仍指向旧快照，新修订建立新的交接和核对；不得静默沿用旧结论。
5. 实际系统不齐：只有 ERP、Excel 排程和纸质检验时，记录真实载体并明确来源；平台不呈现不存在的 MES/QMS 已连接状态。

## 6. 实现边界与数据规则

制造仓库继续承载业务模型、持久化、API 和工作台组件；Agent 平台继续承载认证、权限、页面外壳和共享 Markdown/Mermaid 渲染。新增路由进入平台现有精确授权边界，沿用 owner/admin、CSRF/Origin、私有缓存及只读约束。

新增对象按职责分为系统/数据归属、资料包/修订、交接/回执、准备核对/明细四组。使用独立模型、仓储与服务组织，不继续把所有新字段塞进阶段说明和项目 JSON。引用保持稳定标识；已有项目和阶段只通过明确链接关联，现状文字不自动转成已核实业务数据。

创建和状态动作有业务 UUID 幂等保护；同标识不同内容明确冲突。可变草稿和状态写入使用版本校验；冲突保留用户草稿。跨对象规则、版本冻结、归属唯一性和结论聚合由服务端验证，在同一数据库事务中保持一致。记录生产事实的时间与平台登记时间分开。

状态历史和核对证据持久保存，不能依赖当前项目仅保留最近 200 条的活动数组作为完整审计。列表可分页，页面最近动态可以截取，原始事件不截断。归档/停用保留引用；本轮不提供已引用业务对象的物理删除。

项目/工作台聚合通过统一业务查询服务组合阶段、事项和新增必需核对，不能只更新某个页面的计数或把派生结论作为独立可写字段。历史项目 JSON 与新表之间的写入关系在同一 SQLite 事务中校验，避免多个页面显示相互矛盾的完成状态。

证据先支持原始单据/文件编号、版本和已有证据位置的引用；链接在用户明确点击时按平台现有安全策略打开。服务端不自动抓取任意 URL，不新增独立文件上传与公开分享能力。手工录入来源持续标注，不能冒充已从外部系统校验。

## 7. 后续迭代顺序

1. 本轮：工程资料与版本 → 交接回执 → 准备核对，建立来源、责任和留痕。
2. 供应与执行：需求/正式订单区分、供应承诺、采购/客供与到货/检验分离、工单与批次/SN 引用、执行回执。真实 ERP/MRP/MES 接口在取得契约、样例和授权后逐条接入。
3. 质量与交付：保留原始失败和复测、独立制造方/质量/客户放行、入库/发运/签收/验收独立时点、RMA/8D 与 ECO 回流。
4. 数据与智能：已核实数据和指标口径形成后，再提供可下钻分析、带引用知识能力及受控事务工具。工业设备闭环控制另立工程项目。

本轮不增加未来迭代的空页面、装饰性数字、伪同步记录或规则冒充的 AI 分析。既有 Agent Loop 和 HR/其他工作台不改动。

## 8. 验证与发布要求

- API/数据库：正常闭环与持久化重读，资料修订不覆盖历史，回执版本冲突，缺项不能绕过，旧核对不能套用于新版本，数据归属冲突、幂等和并发冲突，归档引用保持及旧数据可读。
- 组件：真实对象的创建/编辑/处理、项目和来源对象定位、业务线差异、只读、失败保留草稿、手册往返与全文阅读；不以渲染几个菜单代替功能验收。
- 平台：精确路由、身份、CSRF/Origin、401/403、缓存及源码/资源 release 一致。
- 发布：已审查代码先合并主线，再从准确 Git 源码构建；沿用独立不可变制造制品、SQLite 一致性备份和 API-only 切换。重新读取实际运行版本及当前完整维护链，保留其他容器、挂载、网络和 Nginx 配置。
- 工程侧负责真实接口、隔离候选、构建和生产边界；正向测试用临时数据和合成测试主体，浏览器布局与实际业务角色验收仍由用户完成。分别报告已通过、失败与未执行项。

## 9. 设计自检

本轮是一个可独立验收的协同闭环，共用基础对象为其服务。所有未接入的系统能力与人工登记都明确区分；业务状态、平台协同状态和正式外部批准不混用。旧手册、项目、阶段、事项和用户现有文件保留；不根据行业参考生成公司的已确认事实。

## 实施架构复核：适用性与新版本复核

复审两次暴露同一类问题：把固定资料绑定、核对进度与“不适用”结论混在一个阶段约束中，会产生无法验证或无法替代的记录。统一规则为：适用的版本项在创建时绑定资料包中已核对的具体资料，后续不换绑；新版本通过明确替代创建独立记录，默认清除旧结论并从待核对开始。

“不适用”本身也是一次需要证据的业务决定。替代时允许操作者明确重新确认不适用，并填写本次责任人、来源、凭据和原因；它可以在创建替代记录时形成独立结论。不得自动沿用旧版不适用、原批准或完成状态。适用项继续保持待核对，不能借不适用分支接受无绑定的待核对项。原资料、旧证据和替代事件保留，服务端事务校验与页面创建规则一致。

验收补充：普通空绑定/NA资料绑定的待核对版本项被拒绝；有记录依据的不适用项可读；旧版作废后，全不适用资料包的新修订能通过独立不适用确认完成替代；缺少新凭据或直接继承已验证状态均被拒绝。
