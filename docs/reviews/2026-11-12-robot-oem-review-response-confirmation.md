## 1. 两点事实校正：属实，采纳

处置文档第1节对原评审的两处校正，我已对照原依据复核，均成立：

### 1.1 "MES已提料"并未混入平台需求表（校正M4表述）

原评审称料况页"把平台本账字段与原生观察字段混排在同一张表里"，表述过重。实际情况：

- "MES已提料"在同页**独立的**`MesOrderMaterials`组件表中，已带环境标识、读取时间和"需另核对线边实收"提示。
- 平台需求表已有数量依据说明及页级`source_modes`。

M4的真实缺口按处置文档口径修正为：**没有逐项数量、计算输入和关联关系的可追溯来源契约**——不是已经把MES数量并入平台余额。修复时必须保留现有的表级隔离，不得以"统一视图"为名把原生观察并进平台确认数量。

### 1.2 `arrival.record`只能支撑"核实"，不能变成正式收货（校正M2建议）

原评审建议"允许引用到货观察创建任务"。复核模型后确认处置文档的边界更准确：

- `arrival.record`仅有到场编号、位置、包裹数和描述；**没有物料、批次、单位或待检数量**。
- `arrival.match`还依赖既有平台收货。

因此到场观察只能作为"核实到料"类任务的依据，**不能直接作为正式收货或IQC检验依据，不能据此关闭检验**。身份不足→派核实任务；身份齐全→才进入检验结果核对。原生收货行的采集与准入按T3补齐，这个两段式设计是对的。

### 1.3 受控用例的实际路径（补充校正）

处置文档指出受控API用例是"收货20→检验合格20→建立有效预留→交出20/实收18"，与原评审旅程示例"合格12/待检8→实收18"不同。校正成立：合格12/待检8的中间态必须补上后续检验与分配依据才能继续，否则只能办理已有合格且可归属的部分。该场景已正确写入mock spec的验收（§7：合格12/待检8不关闭剩余8）。

## 3. SAP mock spec质量评价：过关

以下关键决定特别认可，实施时不得弱化：

1. **契约层模拟而非页面假JSON**：合成SOAP走真实WSDL解析链（`contracts.parse_wsdl`＋`parse_response`），字段/结构不匹配能在切换实机前暴露。
2. **默认关闭、源读取失败不静默退mock**：防止mock事实在故障时悄悄顶替真实读取。
3. **`origins`并集传播**：任一模拟输入使派生结论持续标为模拟；"平台确认"不能掩盖`mock`来源。
4. **51条不截成50声称完整**；当前接口无经核实的分页契约，不发明下一页参数。
5. **实机接入后旧mock历史保留原身份**，不原地改写为真实记录。
6. **脱敏fixture**保留字段、类型、长度、精度与SOAP action，移除端点、账号和真实业务标识。

## 4. 两点实施提醒

1. **`source_modes`页级汇总与逐项身份必须从同一数据源派生。** 避免页级说"含模拟"而逐项查不到是哪一项。mock spec §4末段已有此要求（"页级汇总不能替代逐项身份"），建议在T2实施计划中给它一条独立验收。
2. **M6的大集合测试数据提前到T2准备。** M6验收样本（单项目51+条物料责任事项、跨项目尾页可达）虽然排在第四步，但T2做来源投影时就应准备好这批测试数据——否则到T6才发现投影查询在大集合下的分页行为问题，会返工T2的投影层。
