# 机器人OEM产品评审核对与修订处置

日期：2026-11-12。核对代码：本地`main`的`5a6a620`。依据：[Claude评审](2026-11-12-robot-oem-product-review-claude.md)、[原评审材料](2026-11-12-robot-oem-product-review-brief.md)及当前实现。本文记录核对结论与开发要求，表内修正项均尚未实现。

## 1. 结论和需要校正的事实

采纳M1—M6所指的产品缺口：首期需要修复同一需求内的办理、解除任务对重复本地登账的依赖、补足数量来源、保证岗位物料待办完整。全量导航改版和连续多段物流继续后置。

三处表述需要澄清，防止修错边界：

1. **M4的具体表现**：平台需求表没有MES已提料列；该列在同页`MesOrderMaterials`的独立组件表中，已有环境、读取时间和“需另核对线边实收”提示。平台表也已有数量依据说明及页级`source_modes`。缺口是**没有逐项数量、计算输入和关联关系的可追溯来源契约**，不是已经把MES已提料并入平台余额。修复时保留这条隔离。
2. **M2的复用前提**：`arrival.record`仅支持人工包裹到场观察：到场编号、位置、包裹数和描述。没有物料、批次、单位或待检数量；`arrival.match`还依赖既有平台收货。可将其作为“核实到料”的任务依据，不能直接变成正式收货/IQC结果或据此关闭检验。当前也没有可直接复用的原生收货行采集与准入，应按T3补齐。
3. **完整旅程的证据**：受控API用例在收货20后先检验合格20、建立有效预留，再交出20/实收18。评审示例“合格12/待检8→实收18”中间必须补上后续检验与分配依据；否则只能继续办理已有合格且可归属的部分。API通过不能证明所有页面步骤已经连贯，更不能证明生产同单闭环。

设计授权记录已补在[主设计](../superpowers/specs/2026-11-11-robot-oem-material-workbench-design.md)开头：以本次接续会话中用户明确要求设计、开始开发、按完整工作流继续的指令为依据，记录方向及分批开发授权；没有补造逐页、逐字段或发布日期的专项签批。SAP契约mock有用户明确启动指令，具体规范见[新增spec](../superpowers/specs/2026-11-12-sap-mrp-contract-mock-design.md)。

| M2 解除重复本地登账 | `OpenMaterialTask`必须有本地需求；IQC还必须有`supply_receipts`，查料必须有本地交接，后端同样校验 | T3：按可核实的观察/原生对象建立任务引用；身份不足办理核实，身份齐全才进入检验结果核对 | 只有到场观察时能派核实任务；原生对象已核实时无须手工重录正式收货。观察、正式检验和数量满足分别验收 |

| M4 数量来源身份 | 有底层`SourceRef`及原生绑定，但`MaterialControlPage`数量没有逐项来源身份和输入关联 | T2先交来源契约，T1/T3/T5接续；按来源方式、环境、事实角色分别表达 | 模拟持续标识，来源未知明确保留；派生结果可追到输入，原生观察不自动成为平台分配/质量/实收 |
| M5 SAP契约mock规范 | 存在真实BAPI请求/解析服务，现有业务模拟器不是该BAPI mock；此前无专项spec | T1扩展，先满足M4，再按新增spec实现 | 真实契约解析器处理合成SOAP；七个场景有隔离测试、业务页面及宿主验证；断线不自动切mock |

M1的交出与签收均为平台本地事实声明；执行生产MES/WMS作业仍受[只读规则](../../AGENTS.md)限制。M2的观察引用不能建立隐藏的正式收货、供应承诺或库存记录。

## 3. 这轮的最小产品修订

**项目侧**：工作台或“计划与物料”→项目料况→需求详情；同一处安排IQC/核实、跟进急料、交接、实收与查料。需求选中状态和筛选由既有`MaterialViewContext`承载，办理面板使用同一对象和业务命令。

**岗位侧**：事项→本人有权处理的具体对象→接手/反馈/签收/差异；完成后回到原待办范围。复用`GlobalTasks`及任务/交接详情，不增加另一份“我的待办”。

**来源展示**：常规数量只显示简短身份和时间，依据按需展开。来源方式为原生读取、人工声明、文件或模拟；事实角色为平台确认、原生观察或待核实；环境独立标识。平台确认的模拟记录仍须标为模拟，不能被“平台确认”掩盖。

**本地登记**：保留作为有依据的例外声明，普通主旅程不强制使用。已核实的原生单据在后台持久保存引用/观察投影，用户只核对关联，不重复输入源数量。真实收货/检验映射尚未明确时，给可接手的核实事项，不用模拟数据填补生产证据。

## 4. 实施依赖与验收顺序

1. **T2 / M4**：数量来源契约。允许与纯页面入口修复独立开发；是SAP mock进入业务页的前置。
2. **T3 / M2**：观察/原生对象任务引用，区分核实与检验；先完成无原生凭据也能交给人核实的路径。
3. **T5＋T2 / M1、M3**：料况内交接和实收、侧栏直达；复用原有指定人、CAS、幂等和草稿隔离。
4. **T6 / M6**：完整岗位物料事项。与前两项可独立开发；主旅程验收前必须完成。
5. **T1 / M5**：真实SAP契约mock进入隔离项目；遵循专项spec的场景与失败行为。

以上完成后，再扩展T6全项目行动总览；不等生产SAP就绪才开发，也不以mock证明生产同单关联。

## 5. 首期整体验收

- MC从料况发现需求20、带依据设置需要时间、发起急料；有观察无正式收货时能分派核实；有准确检验对象时就地安排IQC。
- IQC从事项接手；先得到合格12/待检8，页面保留8待检和相应缺口；后续结果足以支持20且分配已核实后，继续交接。
- 仓库在需求内登记交出20；指定接收人实收18；查料“找到2”后仍待补收；指定人补签2并建立准确补收关系后，后台重新核对才能结束。该受控样本不引入未核实的中转多段。
- 单项目51条以上物料责任事项、跨项目、撤权、重复点击、超时、旧响应、更换项目/用户/API以及保存期间导航，都不丢待办、不串对象、不覆盖新草稿。
- 真实SAP契约mock仅在隔离项目启用，标识贯穿列表、详情、证据与派生判断。生产MES观察可单独只读核查，不能与模拟SAP合成“生产齐套”。
- 自动化API、页面旅程、真实接口读取、现场岗位走查和生产切换分别记结果。现场走查记录切页、找人、重复录入及等待基线；未走查不写“真实岗位已验收”。
