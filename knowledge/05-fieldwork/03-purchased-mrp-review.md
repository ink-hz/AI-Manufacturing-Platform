# 已采购 MRP 系统的接手核查清单

已知背景仅为“IT 部采购过相关系统”。产品名、厂商、版本、模块、部署、上线状态和实际使用情况尚待确认。整理日期：2026-10-27。以下用于准备与 IT、计划部门和实施服务商的沟通，不预设系统能力或采购结论。

## 首先确认买的是什么

MRP 既可能是某套 ERP 的功能，也可能包含在独立计划产品或更广的制造套件中。业务人员口中的“MRP 系统”和合同中的产品范围不一定相同。先获取产品全名、厂商、版本、已购模块、实施范围、验收文件和当前用户角色，再讨论能否接入 Agent 平台。

| 需要取得的信息 | 应避免的误判 |
| --- | --- |
| 产品名称、厂商、版本与部署方式 | 看到 MRP 缩写就判断产品和接口能力 |
| 合同模块与许可证限制 | 将演示功能视为已购买功能 |
| 实施与验收范围 | 将采购完成视为业务上线完成 |
| 工厂、组织与产品适用范围 | 将一个试点结果推广到所有工厂 |
| 当前实际操作角色与频率 | 用账户数量代表业务使用程度 |
| 数据准备、迁移与初始化记录 | 将系统能打开视为数据能够支持计算 |
| 既有接口及服务边界 | 认为有接口就一定可读写全部业务对象 |

## 一次计算需要哪些输入

让计划人员选一笔已经完成或正在处理的真实需求，说明它如何进入计划、使用哪个 BOM、扣减哪些供应、生成哪些建议。基础原理与可手算的例子见[MRP 演算](../01-foundations/03-mrp-worked-example.md)。

核对输入时，需要同时考虑对象范围和时间：需求是客户要求还是批准后的内部需求；库存截至什么时点；未结采购是否已包含部分收货；生产工单是否已经开工；BOM 版本何时生效；采购与加工提前期如何维护；工作日历采用哪一个。输入缺少这些条件时，一张结果表难以被解释。

| 输入领域 | 要问的具体问题 |
| --- | --- |
| 需求 | 订单、预测、备货、样品和售后需求哪些参与？是否存在需求抵消或重复？ |
| 产品结构 | 按哪个 BOM 和工厂展开？替代料、虚拟件、联副产品是否适用？ |
| 库存 | 哪些质量状态、地点、所有权和专用库存能参与净算？ |
| 供应 | 哪些采购、生产和调拨作为预计接收？取消和逾期怎样处理？ |
| 批量规则 | 按需、固定批量、最小量、包装倍量与安全库存怎样生效？ |
| 时间规则 | 日历、采购、加工、检验、运输和缓冲分别如何建模？ |
| 计划控制 | 计划时界、冻结、确认建议、人工修改与再计划如何处理？ |
| 输出与追溯 | 采购申请、计划订单和异常提示如何形成，能否追到需求来源？ |

不同产品对这些规则的支持和命名可能不同，不能把清单当作所有系统必须原样提供的标准功能。

## 用四个业务样本核查结果

1. **正常需求**：物料齐套、提前期可满足，检查展开、库存扣减和建议日期。
2. **明确缺料**：一个关键料数量不足，检查缺口、影响订单和需要采取的动作。
3. **订单变更**：对已有供应的需求改期或减少，检查系统如何提示调整已有供应。
4. **数据异常**：BOM 生效不一致、待检料被计为可用或供应未及时更新，检查差异能否解释并定位。

每例记录原始输入、运行参数、运行时间、输出、人工判断和处理结果。若需复算，保存原始失败与调整原因；不要连续改参数直到表面正确，却说不清为什么。

## 结果失真时怎样排查

“系统算错了”只是现象。按需求、产品结构、库存与未结供应、计划参数、时间规则、接口新鲜度、算法与配置的顺序，沿原始业务对象追踪。先确认实际输入，再判断是数据、规则、操作还是软件缺陷。重复出现同类差异时，要核查职责和数据契约，不能长期靠人工更改建议维持表面可用。

对“有库存仍缺料”，先看库存状态、地点、占用和时点；对“买太多”，先看需求重复、批量规则和未结供应；对“总是来不及”，先看提前期与日历以及计划生成时点。它们都是排查方向，不能仅凭现象直接下结论。

## 将来怎样接入业务工作台

在系统与数据确认之前，可以先建立产品使用说明、字段解释、标准操作与异常案例知识。具备可信只读接口后，再考虑提供需求解释、缺料影响查询和跨系统证据整理。创建采购申请、调整工单或更改主数据需要明确业务授权、真实回执与审计，不能把聊天回复当作原系统已完成动作。

实际对接的下一份输入应当是系统识别资料和一份去除敏感内容的业务样本。当前知识整理不依赖它，后续公司专属说明再据此补充。
