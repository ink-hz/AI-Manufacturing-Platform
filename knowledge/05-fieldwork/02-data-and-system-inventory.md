# 系统与数据盘点模板

整理日期：2026-10-27。以下是可直接复制使用的调研模板，字段由本知识库按制造业务链设计，不表示公司已经拥有这些系统或数据。每张表都应注明负责人、版本、更新时间和确认状态；未确认内容写“待业务核实”，不把猜测填成现状。

## 系统台账

系统采购范围、上线范围和实际使用范围需要分别记录。例如合同里购买了计划模块，并不证明业务部门正在使用该模块生成正式计划。

| 字段 | 要记录的内容 |
| --- | --- |
| 系统编号与名称 | 内部唯一编号、产品名、厂商和实施服务商 |
| 产品与部署版本 | 软件版本、补丁、云端或本地、生产与测试环境 |
| 采购与上线范围 | 已购模块、授权限制、已上线组织与工厂、尚未启用模块 |
| 业务范围 | 服务哪些流程、哪些产品和订单类型 |
| 业务负责人 | 谁确认业务规则与结果，谁主持业务验收 |
| 技术负责人 | 谁维护运行、集成、账号和故障处理 |
| 用户与关键岗位 | 实际用户角色、活跃使用情况、培训与替补人员 |
| 核心对象 | 物料、BOM、工单、库存、检验、客户等 |
| 权威数据范围 | 哪些字段由该系统维护，谁能批准变更 |
| 上下游关系 | 系统编号、交换对象、方向、方式和频率 |
| 身份与权限 | 登录方式、角色来源、外部访问和权限复核责任 |
| 运维与连续性 | 监控、备份、恢复验证、支持时间和业务影响 |
| 商务与服务边界 | 合同范围、接口授权、服务约定和续费责任 |
| 问题与证据 | 实际失败样本、业务影响、处理状态、证据链接 |
| 生命周期 | 当前使用、待上线、计划退出及退出条件 |

## 业务对象与字段字典

| 对象 | 关键字段 | 权威维护角色 | 下游使用方 | 必须核对的问题 |
| --- | --- | --- | --- | --- |
| 物料 | 编码、名称、规格、基本单位、采购单位、状态 | 待业务核实 | 研发、计划、采购、仓库、制造 | 单位与换算是否一致，停用是否影响存量业务 |
| BOM | 父子物料、用量、版本、适用工厂、生效条件 | 待业务核实 | 计划、工艺、生产、核算 | 计划使用哪个版本，在制品如何处理变更 |
| 工艺路线 | 工序、资源、准备时间、加工时间、替代路线 | 待业务核实 | 排程、现场、成本 | 标准工时是否适用实际批量与资源 |
| 库存 | 物料、地点、批次、质量状态、数量、单位 | 待业务核实 | 计划、领料、出货、核算 | 账面数量与可用数量如何转换 |
| 生产工单 | 产品、数量、版本、日期、状态、需求来源 | 待业务核实 | 仓库、现场、质量、核算 | 下达、开工、完工与结案各代表什么 |
| 采购订单 | 供应商、物料、数量、承诺日、收货情况 | 待业务核实 | 计划、仓库、检验 | 未结数量、冻结与取消是否及时反映 |
| 检验记录 | 对象、规范版本、样本、原始结果、判定 | 待业务核实 | 仓库、生产、质量追溯 | 放行人、原始数据和复检能否对应 |
| 产品序列号 | 产品、配置、部件关系、工序与测试历史 | 待业务核实 | 制造、服务、质量 | 拆换件、返工、返修后关系如何更新 |
| 工程变更 | 变更对象、前后版本、批准、生效、处置 | 待业务核实 | 研发、采购、计划、制造 | 各系统生效范围是否一致 |

同一对象可能由多个系统承载，但字段维护职责应当明确。例如 ERP 维护库存数量、质量系统维护检验结论时，还需要约定结论如何改变可用性、失败时怎样防止错误发料。系统分工不是靠表格写上“唯一来源”就自动成立。

## 接口台账

每一条接口至少记录以下内容：接口编号；业务目的；发送与接收系统；对象与版本；业务唯一标识；触发条件；传输方式；频率；时间与单位；成功回执；失败状态；重试与去重；对账方法；权限；责任人；变更兼容；验收样本。

| 核对场景 | 应当说清的结果 |
| --- | --- |
| 同一工单消息发送两次 | 接收方识别同一次业务动作，结果不会重复增加 |
| 工单取消先于创建消息到达 | 系统有约定的顺序或状态处理方式，不能悄悄恢复已取消任务 |
| 接口返回超时 | 能够查询真实受理结果，避免盲目重复提交 |
| 批次同步中断 | 明确已完成范围与未完成范围，能够核对后续差异 |
| 主数据尚未发布到下游 | 业务记录进入明确的待处理状态，责任方可以纠正 |
| 单位或时间范围不一致 | 数据契约标明换算、精度、时区与业务日期 |
| 人工修正数据 | 保留原因、批准、原值、修改值及后续对账 |

这些是设计与验收问题，具体实现见[系统集成与数字线程](../02-systems/03-integration-and-digital-thread.md)。不能只以网络连通或返回成功作为业务一致性的证明。

## 问题与需求台账

一条问题建议使用以下结构：问题编号、发现人、业务场景、具体对象、发生时间、现象、影响、当前处理方式、原始证据、已证实原因、待验证假设、责任角色、解决候选、验收方法、状态、复核结果。

把“需要一个看板”改写为“计划员每天需要核对某类缺料是否影响承诺交付；当前在哪几份表之间比对，发现差异后怎样处理”。前者是方案，后者才是可研究的业务问题。把问题、需求、方案和项目分开，能够避免为同一问题重复采购功能。

## 抽样与质量盘点

| 数据集 | 可抽取的样本 | 检查项 |
| --- | --- | --- |
| 物料与单位 | 在产产品关键料、易混淆规格、长周期料 | 唯一性、单位、状态、制造商对应 |
| BOM 与变更 | 一个成熟产品、一个新产品、一个发生过变更的产品 | 版本、生效、用量、替代、在制处置 |
| 库存 | 可用、待检、冻结、线边、委外各一类 | 账实、状态、地点、占用与可追溯性 |
| 计划与采购 | 正常交付、缺料延期、订单取消各一笔 | 需求追溯、净算、日期、未结供应 |
| 工单与测试 | 正常、返工、换料、返修各一批 | 过站、耗料、版本、放行与追溯 |

样本用于暴露规则与链路，不代表统计总体。若需要宣称全库准确率，应另外定义总体、抽样方法、数量、时点与误差口径，不能把方便取得的几个样本推广成全公司结论。

## 将结果转成可执行事项

完成盘点后，把工作分为业务规则确认、主数据治理、现有功能启用、系统缺陷修复、集成改造和新能力建设。每项工作都指定业务验收人。相同现象可能需要不同解决办法：缺料表失真既可能来自库存状态错误，也可能来自提前期或需求重复，还可能是接口未更新；需要证据区分。
